# 设计笔记

## 检索

BM25 用中文二元组，没用 jieba。99 条语料上效果差不多，省一个词典加载。

问题字段重复 5 次、同义问法 3 次、正文 1 次。最简单的字段加权。不这么做，「面试要注意什么」会被「挂科」那条抢走，因为「注意」在语料里比「面试」稀有、idf 更高。

虚词单独列了一张表。「什么」「怎么」「可以」占了语料两成，按 df 比例拦不住，留着会把「降转是什么」推到「拟录取是什么意思」那条上去。

门控三档，只看三个能数出来的量：

- 词表覆盖率：问题里的词有多大比例真在语料里。低于 0.55 直接判域外。
- idf 加权覆盖率：命中的词占问题总权重的比例。低于 0.5 判弱命中。
- 原始首位差：第一名和第二名的 BM25 分差。低于 0.55 判弱命中。

最后一个必须用融合前的分数。RRF 会把相邻名次压成 0.016 和 0.016，看那个没法判断。

## 作答

不做真流式。数字校验要等完整答案，边吐边发现抄错了就来不及。

模型只做两件事：从候选段落里挑出相关的，按原话摘句子。不允许补充资料之外的事实，不允许改写数字。

输出是 JSON，`{"cited": [序号], "answer": "..."}`。`cited` 先出，答案基于它生成，这样引用可以用规则校验。

答案里每个数字都要能在引用原文里找到，找不到就整段退回原文。

## 知识库

文档是唯一源，JSON 是生成物，不反向手改。

id 是出生编号。重编号、挪小节都不改，删了留 `removed` 墓碑。这样 `related` 和 `alt_questions` 里的引用不会因为条目换位置而指错。

锚点按站点的 slugger 规则算，跟页面上能点到的位置一一对应。算法复刻了 `github-slugger`：小写、去标点、空白转连字符、重名加后缀。

## 试运行数据

每次问答写一行 JSONL 到 `data/logs/ask-YYYY-MM-DD.jsonl`。三个字段是有意留的：

- `bm25` 是融合前的原始分。RRF 之后相邻名次几乎同分，只看融合分回答不了「为什么这条赢了」。
- `vocab` 是问题里的词有多大比例真在语料里。域外问题靠它兜。
- `request_id` 是 6 位十六进制。前端显示在答案右下角，用户能念出来。

问题原文会脱敏：手机号、身份证、带上下文的 QQ 号都会被替换。不想留原文就把 `FZURUN_LOG_QUERY` 关掉。

反馈走 `POST /api/feedback`。前端点「没帮上」才展开四个原因，选了才发请求。服务端缓存最近 500 条 id 到 query 的映射，反馈晚到也能对上。

一周看一次：

```bash
uv run python scripts/review.py --days 7
```

报告里有门控分布、延迟、零命中榜、弱命中榜，还有差评当时命中的是哪条、bm25 多少。最后给一份能粘进 `alt.json` 的骨架。

怎么读这份报告：

- 反复出现的零命中，八成是同义问法没覆盖，补 `alt.json`，别改算法。
- 差评落在强命中上，说明检索没错，是答案或者条目内容的问题，别去调阈值。
- 差评落在弱命中上，才轮到怀疑检索。

## 踩过的坑

**智谱 Flash 默认开思考。** 4.7-Flash 那次 200 个 token 全花在 `reasoning_content` 上，`content` 是空字符串。项目读的就是 `content`，会当成「资料里没有答案」。必须显式传 `thinking: disabled`，实测 4.5-Flash 从 13.4 秒降到 4.3 秒。

**RRF 会压平分数。** 一开始用融合分算首位差，发现永远判不出强命中。换成融合前的 BM25 原始分才对。

**词表覆盖率要用过滤前的 token。** 一开始用虚词过滤后的 token 算，分母变小，短问句全被判成域外。过滤后的词表里连「什么」都不存在，覆盖率当然低。

**BlackSheep 默认把中文转成 `\uXXXX`。** 用官方 `json_settings.use()` 换序列化器。别把 `json` 这个模块名覆盖成响应函数，lambda 里的 `json.dumps` 会炸。

**`uv sync` 会清掉 `optional-dependencies` 里的工具。** dev 依赖放 PEP 735 的 `[dependency-groups]`，默认就装。
